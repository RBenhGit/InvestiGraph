## משימה 2 — תווית "FAIR VALUE" כשההערכה קרובה למחיר

### הקשר

היום `renderVerdict` (שורה 406) קובע רק שתי אפשרויות: `Undervalued` אם `fairValue > currentPrice`,
אחרת `Overvalued`. אין אזור אמצע. המשתמש רוצה תווית שלישית — `FAIR VALUE` — כשההפרש קטן מספיק.

### קבצים

- `src/web/public/app.js:406` — `renderVerdict`, כאן משנים את הלוגיקה.
- `src/web/public/style.css` — צבע/עיצוב לתווית החדשה (יש כבר `.verdict.good`/`.verdict.bad`,
  תוסיפו `.verdict.neutral` או שם דומה).
- `src/web/public/app.test.js` — טסטים.

### החלטה שצריך לקחת לפני קידוד — הרוחב של הטווח

המשתמש לא ציין אחוז סף. **אל תנחשו בשקט** — זו בדיוק הדוגמה מ-CLAUDE.md ל"כשהבקשה עמומה, הציגו
את האפשרויות". שאלו את המשתמש (או, אם אתם רוצים להתקדם בינתיים, יישמו עם קבוע קל לשינוי):

```js
// המרחק המקסימלי (באחוזים) מהמחיר הנוכחי שעדיין נחשב "הוגן", לא Undervalued/Overvalued.
const FAIR_VALUE_TOLERANCE_PERCENT = 5;
```

הציבו את הקבוע למעלה בקובץ (ליד שאר הקבועים/רכיבי ה-DOM), לא בתוך הפונקציה, כדי שיהיה קל
לשנות אותו אחר כך בלי לחפש בתוך לוגיקה.

### צעדים

1. הוסיפו את הקבוע `FAIR_VALUE_TOLERANCE_PERCENT` בראש הקובץ.
2. שנו את `renderVerdict` כך שבמקום שני מצבים יהיו שלושה:
   ```js
   function renderVerdict(el, fairValue, currentPrice) {
     if (!isValidPrice(currentPrice) || fairValue === null || fairValue === undefined) {
       el.textContent = 'n/a';
       el.className = 'verdict';
       return;
     }
     const diffPercent = (fairValue / currentPrice - 1) * 100;
     if (Math.abs(diffPercent) <= FAIR_VALUE_TOLERANCE_PERCENT) {
       el.textContent = 'FAIR VALUE';
       el.className = 'verdict neutral';
     } else if (diffPercent > 0) {
       el.textContent = 'Undervalued';
       el.className = 'verdict good';
     } else {
       el.textContent = 'Overvalued';
       el.className = 'verdict bad';
     }
   }
   ```
   **שימו לב:** זה גם מתקן side-effect — הפונקציה הקיימת לא בדקה `isValidPrice`/`fairValue`
   בכלל (קוראים לה תמיד עם `result.ok === true`, אז זה כנראה בטוח, אבל ה-guard לא מזיק
   ומתאים לסגנון הקיים בקובץ). אם זה מרגיש כמו "יותר משינוי כירורגי" — אפשר להשאיר את
   ההתנהגות המקורית בלי ה-guard הזה ולהוסיף רק את מקרה ה-FAIR VALUE. שיקול דעת.
3. הוסיפו `.verdict.neutral` ל-`style.css` — צבע ניטרלי (לא ירוק/אדום — למשל אפור/כחול,
   תואם לפלטת הצבעים הקיימת בקובץ, חפשו `--accent` או משתני CSS דומים).
4. **החלטה נוספת:** האם התווית הזו חלה על Lynch, Rule #1, או שניהם בנפרד? `renderVerdict`
   נקראת פעם אחת לכל שיטה בנפרד (דרך `renderScenarioColumn` ודרך הבאנר), אז ברירת המחדל
   הטבעית של הקוד היא **כל שיטה בנפרד** — Lynch יכול להראות FAIR VALUE בזמן ש-Rule #1 מראה
   Overvalued לאותו טיקר. זו כנראה ההתנהגות הנכונה (השיטות בלתי-תלויות לפי CLAUDE.md), אבל
   ציינו את זה למשתמש כשמדווחים שהמשימה הושלמה, למקרה שהוא ציפה למשהו אחר.

### הגדרת "סיימתי"

- טסטים ל-3 המקרים: `fairValue` בטווח (FAIR VALUE), מעל הטווח (Undervalued), מתחת (Overvalued),
  ומקרה קצה `currentPrice: 0`.
- אימות ויזואלי בדפדפן על טיקר שבאמת נמצא קרוב לשווי ההוגן (אפשר גם לשנות זמנית את
  `FAIR_VALUE_TOLERANCE_PERCENT` לערך גדול כמו 100 כדי לוודא שהתווית בכלל מופיעה, ואז להחזיר).

### שלב 1: מודול `src/evaluators/` — Backend קודם, בלי UI

**למה קודם ה-backend:** כי אפשר לבדוק אותו לגמרי עם טסטים, בלי דפדפן, ולוודא שהוא נכון לפני
שבונים UI מעליו. זה גם התבנית שהפרויקט הזה כבר משתמש בה בכל מקום (`src/history/`).

1. הסתכלו על `src/history/store.ts` ו-`src/history/types.ts` כדוגמה חיה — תעתיקו את התבנית,
   לא תמציאו חדשה. שימו לב במיוחד ל:
   - `resolveHistoryFilePath` בקובץ `store.ts` — איך הוא בונה נתיב ברירת מחדל + env var
     override (`HISTORY_FILE_PATH`). תעשו את אותו הדבר עם `EVALUATORS_FILE_PATH` וקובץ
     ברירת מחדל `evaluators.json` בשורש הפרויקט.
   - טיפול בקובץ פגום/ריק (ב-`readHistoryFile`, יש שם לוגיקת סינון רשומות לא-תקינות עם
     `console.warn`) — אותו רעיון, פשוט יותר כי כאן זו רשימת שמות, לא רשומות מורכבות.
2. `types.ts` — הגדירו טיפוס פשוט:
   ```ts
   export interface Evaluator {
     name: string;
   }
   export type EvaluatorsResult<T> =
     | { ok: true; data: T }
     | { ok: false; error: { type: 'IO_ERROR' | 'INVALID_INPUT'; message: string } };
   ```
   (אפשר להתחיל מ-`string[]` בלבד במקום `Evaluator[]` אם זה מספיק פשוט — אין כרגע צורך בשדות

     **בלבד**. אל תיגעו בקובץ `history.json` בשום שלב בפונקציה הזו — זו בדיוק הערבות
     שהמשתמש ביקש (מחיקה לא פוגעת בהיסטוריה).
5. כתבו טסטים ל-3 הפונקציות: הוספה, הוספה כפולה (לא אמורה ליצור כפילות), מחיקה, מחיקת שם

### צעדים

1. קודם תחליטו: הדה-דופ ("רק האחרונה") קורה בצד השרת או בצד הלקוח? **המלצה: צד הלקוח**,

2. ב-`valuations.js`, כתבו פונקציה טהורה (קל לבדוק בטסט, בלי DOM):
   ```js
   /** מחזיר רק את הרשומה העדכנית ביותר לכל צירוף (ticker, evaluator). */
   function dedupeToLatest(records) {
     const latestByKey = new Map();
     for (const record of records) {
       const key = `${record.ticker}::${record.evaluator ?? ''}`;
       const existing = latestByKey.get(key);
       if (!existing || new Date(record.evaluatedAt) > new Date(existing.evaluatedAt)) {
         latestByKey.set(key, record);
       }
     }
     return Array.from(latestByKey.values());
   }
   ```
   שימו לב לנקודה עדינה: רשומה בלי `evaluator` (רשומות ישנות שנשמרו לפני משימה 1) מקבלת
   מפתח עם `''` — כל הרשומות הישנות-בלי-evaluator מאותו טיקר מתחרות זו בזו כאילו הן מאותו
   "מעריך" (הריק). זו התנהגות סבירה למעבר, אבל **תעדו את זה בהערה בקוד**, כדי שהמפתח הבא
   לא יחשוב שזו טעות.
3. שלפו את שדה ה-`base` בכל רשומה — זכרו את הכלל מ-CLAUDE.md: `record.base ?? record`
   (כי רשומות ישנות שמורות בפורמט שטוח, לא מקונן). דוגמה:
   ```js
   function getBaseScenario(record) {
     return record.base ?? record; // legacy flat records have no .base, they ARE the base
   }
   ```
4. בנו את הטבלה: עמודות מוצעות — טיקר, מעריך, תאריך, שווי הוגן Lynch, שווי הוגן Rule #1,

5. טענו נתונים ב-`fetch('/api/history')` בטעינת הדף (`DOMContentLoaded` או ישירות אם

6. כתבו טסטים ל-`dedupeToLatest` ול-`getBaseScenario` בפני עצמן (פונקציות טהורות = קל

## משימה 6 — מיון וסינון על הטבלה החדשה

**אותה פרוסה כמו משימה 5 — לא commit נפרד בהכרח, אבל מומלץ עדיין להפריד לשני commits קטנים
כדי שקל יהיה לבדוק/לבטל כל חלק בנפרד אם צריך.**

### הקשר

`GET /api/history` כבר תומך בסינון לפי טיקר (סינון שרת-צד). כל השאר (מיון, סינון לפי מעריך,
אולי טווח תאריכים) — **המלצה: לגמרי צד לקוח**, כי הנתון כבר נמצא כולו בזיכרון אחרי משימה 5
(שם כבר הבאתם את כל ה-history ל-JS). אין סיבה להוסיף round-trip לשרת בשביל מיון של מערך
שכבר קיים.

### קבצים

- `src/web/public/valuations.js` — כל השינוי כאן.
- `src/web/public/valuations.html` — כותרות עמודות לחיצות + שדות סינון.

### צעדים

1. שמרו את הרשימה המקורית (אחרי `dedupeToLatest`) במשתנה מודול (`let allRecords = [];`),
   ותציגו תמיד גרסה מסוננת/ממוינת שנגזרת ממנה — **אל תשנו את `allRecords` עצמו** בזמן
   מיון/סינון, כדי שאפשר לנקות סינון ולחזור לכל הנתונים בלי fetch מחדש.
2. מיון: על כל כותרת עמודה לחיצה, שמרו state קטן (`{ column: 'ticker', direction: 'asc' }`),
   וכתבו פונקציה טהורה `sortRecords(records, column, direction)` — שוב, קל לבדוק בלי DOM.
   שימו לב ל-type של כל עמודה: מחרוזת (טיקר, מעריך) צריכה מיון אלפביתי, תאריך צריך המרה
   ל-`Date`, מספר (שווי הוגן) צריך להשוות כמספרים לא כמחרוזות (אחרת "10" < "9" לקסיקוגרפית).
3. סינון: שדה טקסט לטיקר (כבר יש דוגמה כמעט זהה ב-`historyFilter`/`fetchHistory` ב-`app.js`,
   שורות 37-38 ו-472+ — התבנית שם רלוונטית גם כאן, גם אם כאן זה סינון בזיכרון ולא בקשת
   רשת), ו-dropdown לסינון לפי מעריך (מלאו את האופציות מתוך הערכים הקיימים ב-`allRecords`,
   לא מ-`GET /api/evaluators` — כי כאן רוצים רק מעריכים שבאמת יש להם רשומות, לא כל הרשימה
   המנוהלת).
4. כל שינוי בסינון/מיון מפעיל מחדש רנדור של הטבלה מ-`allRecords` דרך הפייפליין
