# שיטות הערכת שווי

← [Home](Home.md)

שתי הפונקציות ב‑`src/valuation/` **טהורות לחלוטין** — אין רשת, אין קריאת קובץ, אין תלות
בשעון. הקלט מגיע מוכן משכבת ה‑`data/`.

## Clamp — לפני הכול

```ts
// src/valuation/shared/clampGrowthRate.ts
GROWTH_RATE_FLOOR_PERCENT = -5
GROWTH_RATE_CAP_PERCENT   = 25
```

**שתי השיטות** קוראות ל‑`clampGrowthRate` **פנימית** — הקוראים (CLI/web) מעבירים את הקצב
הגולמי, לא מהודק. זה שומר על `inputs.growthRatePercentRaw` (הגולמי) ו‑
`inputs.growthRatePercentClamped` (אחרי ה‑clamp) שניהם גלויים בתוצאה — חשוב לתצוגה, כדי
שהמשתמש יראה מתי הוזן ערך קיצוני.

## Method A — Lynch / PEG

```
FairValue = EPS(ttm) × growthRatePercentClamped
```

**ללא היוון.** הכי פשוט משתי השיטות. שגיאות אפשריות: `MISSING_EPS`,
`NEGATIVE_OR_ZERO_EPS`, `MISSING_GROWTH_RATE`.

## Method B — Rule #1 (מכפיל יציאה מהוון)

```
epsFuture   = epsTtm × (1 + g)^years
futurePrice = epsFuture × exitPeMultiple
fairValue   = futurePrice / (1 + r)^years
```

כאשר `g = growthRatePercentClamped / 100`, `r = requiredReturnPercent / 100`.

**חשוב:** זו הקרנת EPS יחידה + מכפיל יציאה + היוון פעם אחת — **לא DCF** עם תזרים מזומנים
שנתי מוקרן. `CLAUDE.md`/הקוד עצמם מדגישים את זה במפורש ("still not DCF").

שגיאות נוספות מעבר ל‑Method A: `INVALID_EXIT_PE` (`exitPeMultiple <= 0`),
`INVALID_REQUIRED_RETURN` (`requiredReturnPercent <= 0`), `INVALID_YEARS` (לא שלם חיובי),
`INVALID_MOS` (ראה למטה).

### Margin of Safety (מרווח ביטחון) — נוסף 2026-08-19

פרמטר שישי אופציונלי, `mosPercent` (ברירת מחדל `0`), מהוון את "מחיר המדבקה" (`fairValue`
של Method B) למחיר קנייה יעד:

```
fairValue = stickerPrice × (1 - mosPercent / 100)
```

`calculateRuleOneValue` עצמה מקבלת **כל ערך** ב‑`[0, 100)` — מחוץ לטווח מחזיר
`INVALID_MOS`. **ה‑UI באתר מגביל בפועל לארבעה ערכים בלבד** (0%/10%/25%/50%, ברירת מחדל
25%) דרך `<select>` קבוע — זו מוסכמת ממשק, לא אילוץ שהפונקציה הטהורה או דגל ה‑CLI
(`-m/--mos <percent>`, טקסט חופשי) אוכפים בעצמם.

**ב‑UI של 3 התרחישים (Bear/Base/Bull, ראה "3 תרחישים במקביל" למטה) ה‑`<select>` הזה
הוא יחיד ומשותף** — ממוקם בשורה העליונה של הטופס, לא בטבלת 3 השורות. אותו ערך MoS מוחל
בדיוק אותו הדבר על כל שלושת התרחישים; אין דרך לתת ל‑Bear MoS שונה מ‑Bull דרך ה‑UI.

## 3 תרחישים במקביל — Bear / Base / Bull (רק באתר)

נוסף 2026-08-22. `src/web/server.ts` מחשב את שתי השיטות (Lynch, Rule #1) **שלוש פעמים**
בכל בקשה — Bear/Base/Bull — ומחזיר `lynch`/`ruleOne` כאובייקט `{ base, bear, bull }`
(כל אחד `ValuationResult` מלא) במקום תוצאה שטוחה אחת. ה‑CLI לא משתתף בזה בכלל — הוא
מחשב תמיד רק את Base.

באתר, טבלת 3 השורות (`scenario-assumptions` ב‑`index.html`) נותנת ל‑Bear/Base/Bull כל
אחד שדות Growth/Exit P/E/Req. return **עצמאיים לגמרי** — לא נגזרים זה מזה. הדבר היחיד
המשותף הוא MoS (ראה למעלה).

**נפילת ברירת מחדל** (רק כשהשדה נשאר ריק לגמרי — לא כשהמשתמש הזין ערך, גם אם 0):

| תרחיש | Growth (אם ריק) | Exit P/E | Req. return |
|-------|-------------------|----------|-------------|
| Bear | `effectiveGrowth × 0.75` (או `−3` אם `effectiveGrowth ≤ 0`) | 10 | 15% |
| Bull | `effectiveGrowth × 1.25` (או `+3` אם `effectiveGrowth ≤ 0`) | 20 | 12% |

**באג שנמצא ותוקן (2026-08-22):** בגרסה הראשונה של הפיצ'ה, Exit P/E/Req. return/MoS של
Bear/Bull היו **קבועים מוצפנים בקוד**, מתעלמים לגמרי מהערכים שהמשתמש הקליד בטבלת
ה‑3 שורות — שינוי Req. return בטופס השפיע רק על Base. תוקן עם טסט regression
(`src/web/server.test.ts`, "uses the bear/bull growth, exit-P/E, and required-return the
user actually provided, not hardcoded defaults"). ראה גם [ארכיטקטורה](ארכיטקטורה.md).

## שרשרת הנפילה של שיעור הצמיחה

```
analystEstimate5yPercent ?? historical3yPercent ?? historical1yPercent
```

מוגדרת **בשני המקומות** (`cli/index.ts`, `web/server.ts`) ולא בשכבת ה‑valuation — כדי
שהפונקציות הטהורות יישארו טהורות ויקבלו כל קלט במפורש. באתר המשתמש יכול לדרוס את הבחירה
הזו ידנית (שדה הצמיחה בטופס).

**באג שנמצא ותוקן (2026-08-21):** השרשרת הזו סטתה בין שני המתאמים בלי שאף אחד ישים לב.
`server.ts` (לא `cli/index.ts`) הוסיף שתי התנהגויות נוספות, אף אחת מהן מתועדת או בדוקה:

1. **תקרה סמויה של 15%** על הערך ההיסטורי (`Math.min(hist, 15)`) — לא קיימת ב‑CLI, לא
   קיימת ב‑`clampGrowthRate` הרשמי (שהוא [-5%, 25%]). לדוגמה: מניה עם צמיחה היסטורית
   אמיתית של 204% (NVDA, 3Y CAGR, אומת חי) הייתה מקבלת שיעור צמיחה שונה לגמרי בין ה‑CLI
   (204%, ואז מהודק ל‑25% ע"י ה‑clamp הרשמי) לבין האתר (נחתך ל‑15% *לפני* ה‑clamp) —
   הבדל של עד ~47% בשווי ההוגן הסופי על אותם נתונים בדיוק.
2. **ברירת מחדל שגויה של 0%** כששלושת המקורות ריקים — במקום להשאיר את הערך `null` (כמו
   ה‑CLI, שמחזיר `MISSING_GROWTH_RATE`), האתר קבע `effectiveGrowth = 0`, וזה יצר הערכת
   שווי מזויפת של $0 עם `ok: true` ובלי שום הודעת שגיאה. אומת חי מול RKLB (מניה אמיתית
   עם כל ארבעת שדות הצמיחה `null` ברמת ה‑API הנוכחית).

שני הבאגים תוקנו — `server.ts` משתמש עכשיו באותה שרשרת בדיוק כמו ה‑CLI, ללא תקרה נוספת
וללא ברירת מחדל ל‑0. **כלל לעתיד:** כל שינוי בשרשרת הנפילה חייב להתעדכן בשני המקומות
יחד ולהיבדק בטסטים בשניהם — הבאג הזה שרד בלי שנתפס כי לא היה שום טסט שמכסה את שני
המקרים (תקרה + כל המקורות ריקים) בצד השרת.

## `HistoricalPeAverages` — שם מטעה, לתשומת לב

השדות נקראים `avg1y`/`avg3y`/`avg5y` אבל `historicalPe.ts` מחשב **חציון**, לא ממוצע —
מאז `4d54b50`. הסיבה: עם 1–5 נקודות בחלון, שנה חריגה אחת (למשל EPS שקוע זמנית) הייתה
שולטת בממוצע; החציון עמיד יותר, במחיר של לא להיות "ממוצע" פשוטו כמשמעו. כלל הסף:
לפחות `ceil(windowSize / 2)` נקודות תקינות כדי שהחלון לא יהיה `null`.

נקודת P/E אחת לשנת כספים = `close הקרוב-הקודם ביותר / dilutedEps` (EPS לא‑חיובי → נקודה
פסולה, מסוננת החוצה, לא נופלת את כל החלון).

**החלטה פתוחה:** האם לשנות את שמות השדות ל‑`median1y/3y/5y`? נוגע ב‑6+ קבצים כולל ה‑UI.
נדונה ב‑[`TASKS.md`](../TASKS.md) משימה 2 — לא הוכרעה כאן.
